# Notification Platform — требования

Пункты 1–7 относятся ко всей платформе. [RFC](rfc.md) детализирует критичную доставку. Числа ниже — проектные цели.

## Бизнес-цели и границы

| ID    | Цель и проверка                                                                                                                                                      |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BG-01 | Retention +15% относительно контроля: предложен D30 — доля когорты регистрации, совершившая значимое банковское действие на 30-й день. Например, 40% →46%, а не 55%. |
| BG-02 | Жалобы −30%: обращения об уведомлениях на 1 000 охваченных пользователей за 30 дней относительно сопоставимого контроля; дополнительно абсолютное число и причины.   |
| BG-03 | Подтверждённая критичная связь: сохранность принятого, доля/время доставок, каждый неподтверждённый случай и его причина.                                            |

Эффект BG-01/02 проверяется на сопоставимых когортах; надёжный брокер сам его не доказывает. Критичные сообщения ради эксперимента не отключаются.

**Доставлено** — получено положительное подтверждение хотя бы одного канала: push от приложения банка, SMS — отчёт провайдера/оператора по его контракту, email — принятие сервером получателя. Эти основания различаются; приём отправляющим API и прочтение человеком — отдельные события.

Гарантия условна: действительный контакт и разрешённый канал могут доставить/подтвердить в одну из разрешённых попыток до 24 ч. Лимит —32 физических попытки. При исчерпании нет ложного успеха: история и сигнал ответственным. Позднее подтверждение сохраняется с отметкой просрочки. Не обещаем доставку при произвольном отказе всех каналов. Быстрый failover после неизвестного результата может дать push + SMS; повтор события и этот межканальный повтор различаются.

## 1. Функциональные требования

| ID    | Поведение                                                                                                                                                                                                                                                                                                         | Бизнес-связь                       |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| FR-01 | **Единый приём и повторы.** Команды передают уведомления в платформу и получают ID/результат. Повтор события для того же получателя и назначения возвращает существующее уведомление; изменённое содержимое с тем же ключом отклоняется.                                                                          | BG-02/03                           |
| FR-02 | **Типы и каналы.** Платформа доставляет транзакционные, сервисные и маркетинговые сообщения через push, SMS и email; критичные обслуживаются приоритетно.                                                                                                                                                         | BG-01/03                           |
| FR-03 | **Настройки и обязательность.** Пользователь отключает маркетинг/некритичные сервисные сообщения и выбирает каналы. Критичные уведомления целиком не отключаются: должен оставаться пригодный канал. Недействительность контакта фиксируется; предпочтение соблюдается при failover.                              | BG-01/02/03                        |
| FR-04 | **Управляемая доставка.** При отказе или отсутствии подтверждения платформа переключает разрешённый канал, повторяет временно неудачные попытки в пределах срока/лимита и прекращает новые попытки после известного успеха. Исчерпание фиксируется как неподтверждённая доставка и вызывает сигнал ответственным. | BG-03                              |
| FR-05 | **Массовые кампании.** Сотрудник запускает кампанию до 1 млн получателей и видит прогресс. Повторяющиеся получатели исключаются; настройки и лимит до пяти маркетинговых сообщений пользователю в сутки суммарно по каналам соблюдаются.                                                                          | BG-01/02                           |
| FR-06 | **Контроль результата.** Уполномоченный сотрудник видит статус, попытки, время, причины переключений и основание подтверждения. Отчёты показывают задержки, недоставки и повторы по типам/каналам.                                                                                                                | BG-02/03                           |
| FR-07 | **Политика стоимости.** Предпочтительный канал пользователя ставится первым; без предпочтения используется push → SMS → email среди разрешённых пригодных каналов. Платформа учитывает все платные попытки и стоимость подтверждённого уведомления.                                                               | BG-03; ограничение стоимости из ТЗ |

Обязательность критичных сообщений, порядок каналов и лимит маркетинга — продуктовые допущения HW4. Пять сообщений — верхняя граница, не обязательная рассылка.

<a id="nfr"></a>

## 2. Нефункциональные требования

`t0` — надёжное сохранение принятого уведомления до успешного ответа источнику. Задержка от банковской операции до t0 измеряется отдельно. p99/p95 — порог для 99%/95% случаев.

| ID     | Качество и измеримые условия                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Связь с FR |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| NFR-01 | **Задержка и failover.** 99% критичных уведомлений начинают первую попытку ≤1 с от t0; при ответе исправного провайдера ≤0,5 с его принятие получено для 99% ≤2 с. В испытании с нагрузкой NFR-02 ≥99,9% подтверждены ≤30 с: хотя бы один разрешённый канал подтверждает в своём бюджете (push ≤5 с, SMS/email ≤10 с). После отказа/таймаута следующий канал начинается ≤1 с; проверяются все порядки предпочтений. В эксплуатации доля ≤30 с считается также среди всех принятых, включая неуспех. | FR-02/04   |
| NFR-02 | **Ёмкость и изоляция.** 30 млн логических уведомлений/сутки; пик 5 000/с 15 минут, включая до 1 000/с критичных. Кампания 1 млн пригодных получателей начинает все первые попытки ≤15 минут при достаточных квотах/соблюдении настроек и лимитов, сохраняя NFR-01 для критичных. Физические повторы считаются отдельно.                                                                                                                                                                             | FR-02/05   |
| NFR-03 | **Доступность и сохранность.** За скользящие 30 дней ≥99,95% корректных авторизованных запросов в пределах NFR-02 надёжно приняты ≤1 с; ошибки, перегрузка и недоступность входят в неуспех. При отказе любого одного процесса/узла потеря принятого состояния и подтверждённого прогресса — 0, обработка возобновляется ≤60 с. Региональная катастрофа вне этой гарантии.                                                                                                                          | FR-01/04   |
| NFR-04 | **Идемпотентность и состояние.** При конкурентной/повторной передаче события ≥48 ч от первого принятия создаётся 0 новых логических уведомлений. Подтверждённый успех не отменяется поздним событием; известный до разрешения резервной попытки успех запрещает её. Межканальный/внешний exactly-once не обещается, повтор после неизвестного результата учитывается отдельно.                                                                                                                      | FR-01/04   |
| NFR-05 | **Настройки и безопасность.** Изменённые настройки применяются к новым попыткам ≤60 с; более старые/неизвестные настройки не дают права новой отправки. Все операции приёма/просмотра/изменения проходят проверку полномочий, административные изменения аудируются; передача и хранение контактов/содержимого шифруются, подлинность callback проверяется. Уже переданное провайдеру может дойти.                                                                                                  | FR-03/06   |
| NFR-06 | **Наблюдаемость.** Для 100% принятых критичных сообщений история попыток/решений хранится 30 дней; p95 поиска по ID ≤2 с при NFR-02. Исчерпание доставки вызывает сигнал ≤2 минут; отсутствие прогресса 60 с при ожидающей работе — сигнал в следующие ≤2 минут. Секреты/полный текст не попадают в диагностические логи.                                                                                                                                                                           | FR-04/06   |
| NFR-07 | **Эффективность стоимости.** В контрольном сценарии без предпочтения, где ≥95% push подтверждены за 5 с, SMS инициируется ≤5% критичных уведомлений; если успех известен до решения о резерве — 0 новых резервных отправок. Стоимость включает все оплачиваемые попытки, включая неудачные.                                                                                                                                                                                                         | FR-04/07   |

Для NFR-01 здоровый канал должен уложиться именно в свой бюджет, в том числе если push выбран последним. Восстановление за 60 с может нарушить цель 30 с: случай учитывается как нарушение, даже если позднее доставлен. Нагрузку, отказы, квоты и безопасность проверяют испытанием; [расчёты](rfc.md#statistics) не заменяют тест.

<a id="asr"></a>

## 3. Архитектурно значимые требования — ASR

ASR — требование/сочетание требований, существенно меняющее архитектуру. P0 — обязательная пригодность, P1 — важная оптимизация после корректности. Известный успех блокирует резерв; при неизвестном исходе критичная своевременность важнее абсолютного исключения межканального повтора.

| ID / приоритет | ASR и связанные требования                                                    | Почему влияет                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| ASR-01 / P0    | **Быстрая критичная доставка с управляемым резервом.** FR-02/04/07; NFR-01/07 | Нужны короткий путь, ограниченные ожидания и последовательная политика. Быстрый резерв конкурирует с ценой и отсутствием повторов.       |
| ASR-02 / P0    | **Сохранность и корректность при сбоях/повторах.** FR-01/04; NFR-03/04        | Нужны durable-состояние, атомарный приём, устойчивые ID и восстановление. Транзакция нашего хранилища не охватывает чужой API.           |
| ASR-03 / P1    | **Масштабирование с изоляцией критичного потока.** FR-02/05; NFR-01/02        | Кампания требует отдельных ресурсов/квот и ограничения скорости, а не только приоритета в общей очереди.                                 |
| ASR-04 / P0    | **Настройки и объяснимый защищённый результат.** FR-03/06; NFR-05/06          | Перед отправкой нужны актуальные разрешения; подтверждения и история должны быть подлинными, доступными для расследования и защищёнными. |

<a id="asr-consequences"></a>

## 5. Архитектурные последствия ASR

| ASR    | Последствия и цена                                                                                                                                                                       |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ASR-01 | Непакетная обработка, таймеры и последовательные каналы с ограниченным retry. Цена — готовый резерв и возможные межканальные повторы.                                                    |
| ASR-02 | Реплицируемое состояние, transactional outbox, журнал попыток, уникальные ID и атомарные переходы. Цена — дополнительные записи/координация; без надёжного сохранения приём отклоняется. |
| ASR-03 | Изолированные очереди, хранилища/исполнители и провайдерские бюджеты; горизонтальное масштабирование и ограничение массового потока. Цена — резерв инфраструктуры.                       |
| ASR-04 | Проверка актуальных настроек перед отправкой, защищённый callback, история и алерты. Цена — дополнительные проверки; недоступные настройки могут задержать сообщение.                    |

<a id="rejected-solutions"></a>

## 6. Решения, которые не подходят

| Решение                                                                   | Нарушаемый ASR | Причина                                                                                 |
| ------------------------------------------------------------------------- | -------------- | --------------------------------------------------------------------------------------- |
| Отправлять синхронно из перевода, хранить прогресс/таймеры в памяти       | ASR-01/02      | Провайдер задерживает операцию, перезапуск теряет работу.                               |
| Общая FIFO-очередь и пул без резервирования ресурсов/квот                 | ASR-01/03      | Миллион маркетинговых сообщений занимает критичный путь.                                |
| Считать HTTP 200 доставкой или полагаться на exactly-once брокера для SMS | ASR-02/04      | Принятие API не подтверждает доставку; транзакция брокера не охватывает чужую отправку. |

Одновременная отправка во все каналы также проигрывает последовательной политике по цене и повторам. Temporal — подходящая альтернатива, а не запрещённое решение.

## 7. Неопределённости и проверка

| ID   | Неизвестное                                                       | Как проверить                                                                                                                 |
| ---- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| U-01 | Оперативные receipts, их точность, idempotency/status API         | Пилот провайдеров и offline/фоновые тесты Android/iOS; сценарий «вызов выполнен, ответ потерян». Проверить бюджеты 5/10/10 с. |
| U-02 | Реальные пики, размеры, тарифы и аварийные квоты                  | Профиль банковских событий и нагрузочный тест с кампанией/массовым failover; согласование квот и бюджета.                     |
| U-03 | Baseline retention/жалоб и причинный эффект                       | Уточнить когорты/причины обращений и сравнить после созревания D30.                                                           |
| U-04 | Опыт команды, готовая Temporal-платформа и требования ИБ/хранения | Короткий прототип обоих вариантов, оценка поддержки и согласование с владельцем/ИБ; пересмотреть выбор при ином контексте.    |
