# Архитектура маркетплейса

Целевая архитектура маркетплейса и запускаемый каркас одного приложения. **Бизнес-функциональность не реализована.** В репозитории запускается только Marketplace API с `GET /health`; остальные контейнеры на [C4 Container диаграмме](docs/container.md) показывают проектное решение.

## Требования и выбранный вариант

Маркетплейс поддерживает покупателей и продавцов, каталог и поиск товаров, персонализированную ленту, оформление заказов, расчёт и учёт платежей и уведомления о статусах заказов. Выбран **модульный монолит Marketplace API и отдельный Payments Service**.

Монолит объединяет тесно связанные сценарии просмотра и оформления заказа: обращения между его модулями не требуют сети. Payments выделен из-за отдельного жизненного цикла платежа, учёта его результатов и интеграции с банком. У Marketplace API и Payments Service разные базы данных; ни один сервис не обращается к базе другого.

## Домены, ответственность и данные

| Домен | Размещение | Ответственность и данные, которыми владеет |
| --- | --- | --- |
| Пользователи | Модуль Users в Marketplace API | Учётные записи покупателей и продавцов, роли и профили. |
| Каталог | Модуль Catalog в Marketplace API | Карточки товаров, продавец товара, категории, текущие цены и поиск. |
| Лента | Модуль Feed в Marketplace API | Предпочтения категорий покупателей и правила подбора товаров. Карточки и цены получает из Catalog. |
| Заказы | Модуль Orders в Marketplace API | Состав и статус заказа, снимок товара и цены на момент оформления. |
| Уведомления | Часть модуля Orders | Шаблоны и история отправки сообщений о статусах заказа. Отправку выполняет через внешний почтовый провайдер. |
| Платежи | Отдельный Payments Service | Расчёт суммы по зафиксированным позициям заказа, попытки платежа, их статусы и записи учёта. Взаимодействие с банком. |

Модули монолита используют одну физическую БД, но каждый владеет своими таблицами и предоставляет другим модулям внутренний интерфейс. Общих таблиц у Marketplace API и Payments Service нет. Идентификаторы пользователя, товара и заказа могут передаваться между границами; это не даёт получателю права менять чужие данные. Изменение текущей цены в Catalog не меняет сохранённую цену уже созданного заказа.

Персонализация ленты намеренно проста: покупатель выбирает интересные категории, Feed запрашивает товары этих категорий из Catalog и ставит их выше остальных.

## Взаимодействия

| Участники | Когда нужен результат | Способ и назначение |
| --- | --- | --- |
| Web App → Marketplace API | До ответа пользователю | HTTPS API для ленты, поиска, управления товарами и заказами. |
| Feed → Catalog; Orders → Catalog | До ответа пользователю | Внутренние вызовы модулей: подобрать товары; проверить актуальные карточки и цены перед созданием заказа. |
| Marketplace API → Payments Service | До ответа о подготовке или начале оплаты | HTTPS API. Orders передаёт неизменяемый снимок позиций и устойчивый идентификатор попытки платежа; Payments рассчитывает сумму и возвращает состояние операции. |
| Payments Service → банк | Результат может прийти после ответа пользователю | API банка для проведения платежа; результат поступает Payments Service отдельным уведомлением от банка. |
| Payments Service → Marketplace API | Результат может прийти после ответа пользователю | Защищённый HTTPS callback с идентификатором попытки и её итоговым статусом; Orders обновляет заказ. |
| Orders → почтовый провайдер | После изменения статуса заказа | Отправка уведомления покупателю; ошибка отправки не откатывает статус заказа. |

 Результат которого нужен до ответа пользователю, - **синхронное взаимодействие сервисов**; получение результата отдельным сообщением после ответа - **асинхронное взаимодействие**. Это не запрещает выполнять код или несколько запросов параллельно с `async/await`: важно, ждёт ли бизнес-операция результат перед завершением. Внутренние вызовы модулей не являются сетевым взаимодействием отдельных сервисов.

После оформления заказ получает статус `awaiting_payment`. Начало оплаты переводит его в `payment_processing`; подтверждённый результат - в `paid` или `payment_failed`. У Payments Service соответствующие состояния попытки: `created`, `processing`, `succeeded`, `failed`. При долгом ответе банка статус остаётся `processing`: тайм-аут сетевого запроса не означает отказ в оплате.

Повтор запроса после сбоя использует **тот же идентификатор попытки**. Payments Service возвращает уже известное состояние, а при обращении к банку использует защиту от повторного списания. Повторно доставленный итоговый статус не вызывает повторного изменения заказа или уведомления. Новая попытка оплаты после отказа получает новый идентификатор. В целевой реализации Payments Service хранит результат до подтверждения приёма Marketplace API и повторяет доставку при временной ошибке.

## Альтернативы и аргументация

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Выбран: модульный монолит + Payments Service** | Один выпуск для тесно связанных модулей; обращения между Feed, Catalog и Orders без сети; платежи и их данные изолированы. | Монолит масштабируется и выпускается целиком; связь с Payments и банком требует обработки задержек, повторов и временного расхождения статусов. |
| **Полностью сервисная архитектура:** Users, Catalog, Feed, Orders и Payments как отдельные сервисы и БД | Каждый домен можно выпускать и масштабировать отдельно; явные границы владения данными. | Больше развёртываемых компонентов и сетевых зависимостей; сложнее обеспечить согласованность заказа и платежа и проследить ошибку через несколько сервисов. |

Для данного задания нет данных о нагрузке или размере команд, которые оправдывали бы пять отдельных сервисов. Поэтому тесно связанные функции оставлены модулями одного приложения, а Payments выделен по чёткой внешней границе платежной операции и данных учёта.

## Запуск реализованного каркаса

Нужен установленный и запущенный Docker с поддержкой Compose. Выполняйте команды из каталога `hw1/`:

```bash
docker compose up --build -d
curl -i http://localhost:8000/health
```

Ожидаемый HTTP-статус - `200 OK`, тело ответа - `{"status":"ok"}`. Проверить состояние контейнера можно командой `docker compose ps`. Остановить - `docker compose down`.

В Compose запускается только Marketplace API. Endpoint `/health` проверяет доступность процесса FastAPI; базы данных, Payments Service и внешние интеграции пока не реализованы.
